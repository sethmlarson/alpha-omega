

# Vulnerability Reporting

### Triage Tooling

A desktop application, aimed at consolidating the Eclipse Foundation's first-line security triage workflow, was designed and implemented. The effort aims to deliver:

* **A consolidated inbox**: aggregating open vulnerability reports, CVE assignment requests, and time-sensitive project items into one auto-refreshing view  
* **Review and filtering**: dedicated views for vulnerability reports and security advisories with rich sorting and filtering  
* **CVE reservation support**: for reserving and tracking CVE identifiers  
* **Automated verification**: initial checks to help distinguish true from false positives  
* **Scanning integration**: connecting to an automated repository scanning pipeline  
* **Team assignment and issue drafting**: to streamline routing findings to the right project teams and creating tracking issues

The goal of the application is to reduce manual overhead, standardize the triage process, and give our security team a faster, more reliable way to review and respond. Throughout this month, further enhancements have been made:

* The CVE assignments page was substantially redesigned: a table view was replaced with a kanban-style board, filtering by author/project was added, and a guided dialog now handles item resolution (title editing, assignee and label management).  
* Automated triage-message templates were added to give reporters and assignees consistent initial guidance, and a feature to log CVE reservations and assignments to a markdown file was introduced as an audit trail and handover aid.  
* A revalidation feature was added to recheck vulnerabilities after an interrupted or crashed scan run  
* AI-generated-report disclaimers were added to clarify that findings are human-verified before being sent out.

The team also improved its monitoring capabilities through:

* A PoC GitLab-to-Slack integration built to improve visibility over email-only notifications

### AI Generated Reports Triage

# Otterdog 

### SBOM

* Production SBOM Publishing: SBOM uploads to sbom.eclipse.org via the Project Identity Authority (PIA) were moved from the staging endpoint to production, and the earlier, obsolete Otterdog-native upload path was removed, leaving PIA as the single source of truth for Otterdog's software bill of materials ([PR \#733](https://github.com/eclipse-csi/otterdog/pull/733)).

### Fixes and Improvements

* Ruleset Enforcement on Private Repositories: A defect that caused ruleset (branch/repo protection) application to fail on private repositories under certain GitHub plans was fixed, ensuring Otterdog-managed security rulesets are correctly enforced across private repositories ([PR \#731](https://github.com/eclipse-csi/otterdog/pull/731)).  
* Password Store Path Regression Fixed: A regression introduced with the `OTTERDOG_CONFIG_ROOT` change in v1.3.1 caused custom `password_store_dir` overrides in `.otterdog-defaults.json` to be silently ignored, leading to failed credential lookups against the configured `pass` vault. The override path is now loaded correctly again ([PR \#725](https://github.com/eclipse-csi/otterdog/pull/725), [Issue \#717](https://github.com/eclipse-csi/otterdog/issues/717)).

# Open VSX

### Access Token & Trusted Publishing Security

* Token Scoping: A new token type (TPT) was introduced alongside general access token scoping, allowing tokens to be limited by namespace or extension rather than granting blanket access, and refactoring extension processing so files are validated only once per request ([PR \#2034](https://github.com/eclipse-openvsx/openvsx/pull/2034)).  
* Token Storage Hardening: Personal access tokens now use UUIDv7 for their random component and are stored hashed rather than in plain text, reducing the impact of a database compromise ([PR \#2048](https://github.com/eclipse-openvsx/openvsx/pull/2048)).  
* Trusted Publishing (OIDC): Full trusted-publishing support landed, letting CI pipelines exchange a short-lived OIDC token (validated on signature, issuer, audience) for a short-lived (15-minute default) access token instead of storing long-lived publish credentials, with registration anchored on stable provider IDs to prevent spoofing by repository/project rename ([PR \#2000](https://github.com/eclipse-openvsx/openvsx/pull/2000), [Issue \#1534](https://github.com/eclipse-openvsx/openvsx/issues/1534), [PR \#2064](https://github.com/eclipse-openvsx/openvsx/pull/2064)).  
* Auth Error Handling: Publish requests using an inactive or expired token now correctly return 401 instead of 400, and the request body is fully consumed before the error response is sent, preventing load balancers from misreading the exchange as a server error ([PR \#2066](https://github.com/eclipse-openvsx/openvsx/pull/2066)).

### Malware & Namespace Integrity

* Verified-Namespace Enforcement: A new scanner runs on every extension publish and, when a same-name extension already exists on the upstream gallery, enforces that the local namespace is verified before allowing the publish — closing a namespace-impersonation path ([PR \#2074](https://github.com/eclipse-openvsx/openvsx/pull/2074), [Issue \#1954](https://github.com/eclipse-openvsx/openvsx/issues/1954)).  
* Cross-Namespace Dependency Bypass Fixed: Extension dependency resolution previously matched dependent extensions by name only, without checking the fully-qualified `<namespace>.<extension>` id, allowing a same-named extension in a different namespace to satisfy a dependency check it should not have ([PR \#2038](https://github.com/eclipse-openvsx/openvsx/pull/2038)).  
* File Resource Collision Validation: Files extracted from a published VSIX are now checked for name collisions before storage, preventing extracted resources from silently overwriting each other ([PR \#2036](https://github.com/eclipse-openvsx/openvsx/pull/2036)).

### Supply Chain & SBOM

* SBOM Generation Workflows: Three new GitHub Actions workflows generate and upload CycloneDX SBOMs for the server, CLI, and web UI (Docker, Gradle, and Yarn artifacts) to the eclipse-csi/pia SBOM endpoint ([PR \#1999](https://github.com/eclipse-openvsx/openvsx/pull/1999), [Issue \#1610](https://github.com/eclipse-openvsx/openvsx/issues/1610)).

### Resource Exhaustion & Availability Hardening

* Decompression Size Limits: Serving cached VSIX resources via the vscode/unpkg endpoint had no bound on decompressed size, so a highly compressible entry could expand far beyond the upload size limit and exhaust temp-disk storage when repeated across files or versions; extraction now enforces a configurable maximum decompressed size, and the web resource cache now evicts by size rather than entry count ([PR \#2060](https://github.com/eclipse-openvsx/openvsx/pull/2060)).  
* Client-Side Size Pre-Check: The `ovsx` CLI now checks a packaged extension's size against the registry's published limit before uploading, avoiding wasted large uploads that would only fail server-side after full transfer ([PR \#2087](https://github.com/eclipse-openvsx/openvsx/pull/2087), [Issue \#1953](https://github.com/eclipse-openvsx/openvsx/issues/1953)).

### Publisher Account Security

* Resilient Contribution Revocation: Revoking a publisher's contributions (including access tokens) previously failed entirely if revoking the publisher agreement failed first — including when the underlying account was already blocked. The flow now tolerates blocked-user responses and only revokes an agreement if one was actually signed, so access tokens can still be revoked when other steps fail ([PR \#2050](https://github.com/eclipse-openvsx/openvsx/pull/2050), [Issue \#1733](https://github.com/eclipse-openvsx/openvsx/issues/1733)).
